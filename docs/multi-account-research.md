# AnyRouter 多账号与通道调度调研报告

本文档整理 AnyRouter 衍生生态中多账号管理、请求重试调度及所谓“占位/保活”机制的公开开源实现调研结果。供系统未来评估多账号与网关路由扩展时参考；**当前版本维持单账号架构与串行浏览器原则，本文档不作为即时代码实现依据**。

---

## 1. 核心概念界定：“挤入与保活”的本质层级

用户所关注的“高并发时挤进去”、“成功后发请求保活”，在架构上属于**网关代理层（Proxy Routing）与账号调度层**，与底层的“Cookie 会话维持”和“每日签到”是完全独立的三个机制：

| 层级 | 涉及凭证与行为 | 生态常见做法与实际效果 |
| :--- | :--- | :--- |
| **Web 登录/会话层** | 会话 Cookie、WAF 校验 | 仅用于进入控制台与读取已有 Key。Cookie 失效需重新认证，不影响已发放的 API Key。 |
| **签到获赠层** | Session Cookie + 用户标识 | 每日周期性 POST `/api/user/sign_in` 获取免费额度，与推理调用无关。 |
| **网关代理/调度层** | API Key (`sk-...`)、渠道队列 | 负责将用户的 `/v1/chat/completions` 分发至上游。遇到 429/500 时轮询换 Key 重试或队列排队。 |
| **主动探测/保活层** | 独立 API Key、定时推流脚本 | 外部脚本持续轮询请求特定轻量模型，试图在服务空闲或额度生效时“抢占”响应窗口。 |

---

## 2. 网关层调度与多渠道路由核实 (Metapi / NewAPI)

调研核实了 [cita-777/metapi](https://github.com/cita-777/metapi)（基于固定 commit `88634b0d7207039e8d0c0d026c38870cf74bf2bc`）及通用 NewAPI / OneAPI 的路由设计：

### 2.1 凭据解耦与路由算法
- **凭据分离**：在 `upstream-integration.md` 中明确指出 AnyRouter 源自 NewAPI 架构，管理凭据（Session Cookie / 用户身份）仅用于后台拉取配置，推理转发必须使用标准 API Key。
- **候选筛选与熔断**：`src/server/services/tokenRouter.ts#L1854` 实现模型与分组过滤、轮询/权重随机、失败冷却与渠道熔断；`src/server/proxy-core/channelSelection.ts#L79` 仅在初始无候选时触发动态刷新。
- **并发与粘性控制**：`src/server/services/proxyChannelCoordinator.ts#L95` 对部分特定会话提供并发租约队列，默认最大尝试次数为 3（`maxChannelAttempts: 3`）。

### 2.2 关键技术风险与边界
1. **凭证级限流 vs. 站点级容量受限**：
   - 上游 HTTP 429 分为两种：针对单个 Key 的每分钟速率限制（Rate Limit），以及站点整体算力过载（Capacity Exhausted）。
   - 在同站点下配置多个账号的 Key，仅能缓解单 Key 频控，**没有任何公开证据表明换 Key 能绕过站点全局算力饱和**。
2. **流式传输不可重放性**：
   - 现行系统对 `/v1` 提供 1:1 双向透明流式传输。一旦 SSE 首个数据字节（First Byte）已发往客户端，或请求体包含不可重复读取的流，**盲目换渠道重试会导致客户端数据损坏或产生重复扣费**。未来重试必须严格限定在“尚未下发首字节”且“请求体可安全重放”的边界内。

## 3. 开源“保活与占位”脚本事实核验 (Checkalive 分析)

针对社区流传的“保活脚本”，核查了以下两个典型公开项目：

1. **LeafCreeper/Anyrouter-Checkalive** ([源码](https://github.com/LeafCreeper/Anyrouter-Checkalive))：
   - 实现：`scripts/keepalive.sh` 向指定模型（如 `claude-p`）发起推理请求，检查进程退出码；成功后在凌晨按“每 50 分钟运行 5 小时 58 分”循环；`scripts/run-all.sh` 实行持续轮询直至成功。
   - 事实定性：其“先来先用”与“50分钟保活”纯属**作者个人推测的经验阈值，没有任何官方文档证明 AnyRouter 存在会话保活计时器或连接占位机制**。
2. **kw-decade/Ar-Checkalive** ([源码](https://github.com/kw-decade/Ar-Checkalive))：
   - 实现：针对不同模型池持续发送探测请求；项目文档明确声明**不承诺能提高上游优先级**。
   - 语义混淆：日志中将 OpenAI 返回的 `We're currently experiencing high demand` 直接归类为 500 错误，属于项目内部的重试分类逻辑，非 AnyRouter 官方协议。

### 事实结论
- **无优先队列与保活语义**：单次探测成功仅代表该瞬间该模型有空闲容量，并不存在“成功一次后该账号在后续 N 分钟内获得持续优先配额”的机制。
- **探测产生成本**：向实际模型发起的探测请求会真实消耗免费额度或付费余额；无限制的高频重试属于暴力冲击（Hammering），易触发上游 WAF 的 IP 封禁或账号封停。

## 5. 未来多账号架构待决策清单 (Architecture Decisions)

若未来版本评估引入多账号或多渠道支持，必须在实现前决策以下问题：

1. **凭证拓扑映射**：采用“单账号多 Key 轮询”还是“多账号独立隔离池”？前者存储简单但额度受限，后者需要完整的多用户状态管理。
2. **首字节前有界重试 (Bounded Pre-first-byte Retry)**：重试逻辑必须置于网关层，且仅能在上游未输出任何 HTTP Header 与 Body 前拦截（如收到 429/503），最多尝试 2~3 个备用渠道，禁止流式中途重试。
3. **单账号配额与并发预算**：各账号余额与并发是否做本地独立限流，防止单一账号被突发流量耗尽。
4. **拒绝全自动暴力保活**：严禁在后台常驻无意义的模型心跳探测；健康检查应以轻量只读接口为主，避免浪费额度或招致风控。
